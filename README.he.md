# AI-ERP עם n8n

> 🇬🇧 [English version](README.md)

מערכת ERP קטנה ו**לימודית** לעסק אלקטרוניקה ישראלי בדיוני, בנויה מ-**n8n**, **סוכני AI** ו-**RAG**. הכול פשוט בכוונה: תהליכי עבודה קצרים, בלי הפשטות חכמניות, בלי שום דבר להתקין.

שני שירותים נושאים את כל המערכת. **Airtable** הוא גם מסד הנתונים וגם הממשק. **n8n Cloud** מריץ את כל תהליכי העבודה, מארח את הסוכנים, ומפיק את המסמכים כ-PDF לתוך **Google Drive**. בלי Docker, בלי שרת, בלי סביבת הרצה מקומית.

---

## מה יש כאן

- **3 סוכני AI.** סוכן **מנהל** (לבעלים בלבד: אנליטיקה, מסמכים, משימות), סוכן **שירות לקוחות** (פונה לציבור, עונה רק ממידע שאוחזר מהמדיניות ומהקטלוג), וסוכן **מכירות** (פנייה קרה ובדיקת תשובות).
- **9 תהליכי עבודה** — ולידציה של מסמכי מס, קליטת לידים וניקוי כפילויות, פנייה יזומה במכירות, שני צינורות הטמעה (embedding) ל-RAG, וצינור מסמכים HTML←PDF←Drive. קבצי ייצוא לייבוא ישיר נמצאים ב-`workflows/`.
- **RAG** על מסמכי המדיניות של העסק ועל קטלוג המוצרים, מעל מאגר הווקטורים המובנה של n8n.
- **כללי מס ישראליים אמיתיים** — מע"מ 18% (17% לפני 1.1.2025), מספור מסמכים סידורי, וההבחנה בין חשבונית עסקה / חשבונית מס / קבלה — אכופה בקוד.

> **הריפו לא מגיע עם נתונים.** הקובץ `schema/schema.json` מגדיר את 8 הטבלאות; אתם יוצרים אותן וממלאים אותן תוך כדי. מסמכי המקור ל-RAG נמצאים ב-`mock/policies/`.

## ארכיטקטורה

```
                     ┌──────────────┐
  Telegram bot #1 ──▶│              │──▶ Airtable  (the database)
  (manager)          │              │
  Telegram bot #2 ──▶│  n8n Cloud   │──▶ Gmail     (sales emails)
  (customers)        │  + AI agents │──▶ Drive     (documents + PDFs)
                     │  + vectorDB  │
  Gmail  ───────────▶│              │
  Schedules ────────▶└──────────────┘
                            ▲
                            │  chat model · embeddings model
```

הכול חי בתוך n8n Cloud, שנותן לכם כתובת HTTPS ציבורית מהרגע הראשון — כך שבוטים של טלגרם ו-webhooks עובדים בלי מנהרה ובלי port forwarding.

### המודלים

שניהם מוגדרים כ-Credentials ב-n8n וניתנים להחלפה. אף תהליך עבודה לא קשור לספק מסוים.

- **צ'אט** — כל endpoint תואם OpenAI. הצמתים של n8n ידברו איתו ברגע שתדרסו את שדה **Base URL** ב-Credential.
  ⚠️ עם מודל *reasoning*, לעולם אל תגדירו `max_tokens` קטן — ה-`content` יחזור ריק.
- **הטמעות (embeddings)** — endpoint שני תואם OpenAI, וחייב להיות **רב-לשוני**, אחרת עברית מוטמעת גרוע. הוא נפרד בכוונה: endpoint של צ'אט לא בהכרח מגיש `/v1/embeddings`. בדקו לפני שאתם מניחים שאחד מכסה את שניהם.

## התחלה מהירה

### 1. חשבונות

- סביבת **n8n Cloud** — <https://app.n8n.cloud>
- בסיס **Airtable** ו-personal access token — [docs/01-airtable.md](docs/01-airtable.md)
- **שני בוטים בטלגרם** — [docs/02-telegram-bots.md](docs/02-telegram-bots.md)
- **Google OAuth** ל-Gmail ול-Drive — [docs/03-google-oauth.md](docs/03-google-oauth.md)
- endpoint ל**צ'אט** ו-endpoint ל**הטמעות**, שניהם תואמי OpenAI

### 2. בניית בסיס ה-Airtable

צרו את 8 הטבלאות מתוך `schema/schema.json`. הוסיפו לכל טבלת טריגר שדה `Created` מסוג **Created time** — הטריגרים של Airtable נדלקים ממנו ולא יעבדו בלעדיו. הפרטים ב-[docs/01-airtable.md](docs/01-airtable.md).

### 3. הוספת ה-Credentials

**Credentials → New**, אחד לכל שירות, בשמות *מדויקים* כפי שמופיעים ב-[docs/04-workflows.md](docs/04-workflows.md). תהליכי העבודה מפנים ל-Credentials לפי שם, כך שהתאמה הופכת את החיבור ללחיצה אחת.

### 4. הכנסת תהליכי העבודה

אפשר לבנות אותם ידנית בעורך לפי [docs/04-workflows.md](docs/04-workflows.md) — זה התרגיל המועיל יותר — או לייבא את `workflows/*.json` (**Workflows → Import from File**) ולהחליף את ה-placeholders שהדף הזה מרכז בטבלה: מזהה הבסיס שלכם, מזהה הצ'אט שלכם בטלגרם, שני מזהי תיקייה ב-Drive, ושני שמות המודלים.

### 5. מילוי מאגר הווקטורים

הריצו ידנית את **WF6 Policies Embedding** ואת **WF7 Products Embedding**, בסדר הזה, לפני שאתם מפעילים את הסוכנים.
⚠️ ה-Simple Vector Store של n8n יושב **בזיכרון**. הריצו את שניהם מחדש אחרי כל הפעלה מחדש של ה-instance.

### 6. ניסיון ראשון

- שאלו את **בוט התמיכה**: *"מה מדיניות ההחזרות?"* או *"do you have wireless headphones?"*
- שאלו את **בוט המנהל**: *"מה היו הרווחים בחודש שעבר?"* או *"צור משימה להתקשר לספק X"*
- צרו שורת Invoice ב-Airtable ← הוולידציה רצה ← PDF מופיע ב-Drive.

## מבנה הריפו

```
schema/schema.json     ← מקור האמת היחיד (8 טבלאות). הכול קורא מכאן.
mock/policies/         ← מסמכי מדיניות וכללי עסק (*.md) ל-RAG — העלו אותם ל-Drive
templates/             ← HTML של חשבונית / קבלה / הצעת מחיר (עברית, RTL)
workflows/             ← קבצי ייצוא של n8n לייבוא (עם placeholders) + check.mjs
docs/                  ← מדריכי הקמה שלב-אחר-שלב + צילומי מסך של הקנבס
```

שום דבר כאן לא מופעל בפרודקשן. הריפו מחזיק את הסכמה, את התוכן שתהליכי העבודה צורכים, את מדריכי ההקמה, וייצוא ייחוס של כל תהליך עבודה — תהליכי העבודה ה*רצים* חיים ב-n8n Cloud, ושום דבר לא מסתנכרן בחזרה לריפו.

`node workflows/check.mjs` הוא הדבר היחיד שרץ כאן: הוא בודק שקבצי הייצוא הם JSON תקין, שאין חיבורים תלויים באוויר ושאין שמות Credentials לא מתועדים, ואז מריץ את ה-Validate של WF1 מול כללי המע"מ.

אין WF2 — יש חור במספור, לא קובץ חסר.

### איך WF8 מייצר PDF בלי מנוע רינדור

בלי Gotenberg, בלי שירות PDF, בלי בינארי. WF8 קורא את מסמך המקור מ-Airtable, בונה את ה-HTML בתוך הצומת (העותקים הקריאים נמצאים ב-`templates/`), שולח אותו ב-POST ל-endpoint ההעלאה של Drive עם `application/vnd.google-apps.document` כדי ש-Drive ימיר אותו בדרך פנימה, מייצא את ה-Doc הזה בחזרה כ-PDF, שומר את ה-PDF, ומוחק את ה-Doc הזמני. שני צמתי ה-HTTP משתמשים באותו Credential קיים, `Drive OAuth`.

## מגבלות ידועות (מכוונות, לשם הפשטות)

- **מאגר הווקטורים וזיכרון הסוכנים יושבים בזיכרון.** שניהם נמחקים באתחול. הריצו מחדש את WF6 ו-WF7; עד אז הסוכנים עונים "אני לא יודע".
- **אין קבצים מקומיים.** n8n Cloud לא נותן לכם מערכת קבצים, ולכן כל מה שתהליך עבודה קורא מגיע מ-Google Drive או מוטמע בתוך תהליך העבודה עצמו.
- **הטריגרים של Airtable מתשאלים כל דקה לכל היותר** ונדלקים משדה `Created time` — ל-Airtable אין אירוע "on create" אמיתי.
- **המספור הסידורי של המסמכים יכול להתנגש** כששני מסמכים נוצרים בתוך אותו חלון תשאול.
- **Google OAuth במצב "Testing"** מפקיע refresh tokens אחרי 7 ימים.
- **הקשרים הם מפתחות זרים כמחרוזת** (`CUST-0001`), לא קישורים של Airtable.
- **שני דיאגרמות לא מעודכנות.** `docs/diagrams/06-policies-embedding.png` עדיין מצייר קריאה מדיסק ו-`08-file-pipeline.png` עדיין מצייר Gotenberg; שניהם קודמים למעבר ל-Cloud. [docs/04-workflows.md](docs/04-workflows.md) וקבצי הייצוא הם הנכונים.

כל אחת מאלה היא תרגיל המשך הגון: להחליף את ה-Simple Vector Store ב-Qdrant או ב-PGVector, להעביר את המספור מאחורי נעילה, לפרסם את מסך ההסכמה של OAuth.
